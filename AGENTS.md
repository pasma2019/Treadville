# TREADVILLE — AGENT OPERATING SYSTEM

> This document is the governing product, design, UX, engineering, and quality standard for the Treadville digital commerce experience.
>
> Every AI coding agent working in this repository MUST read and follow this document before making changes.

---

# 01 — NORTH STAR

Treadville is not being built as a generic Kenyan SME website.

It is being built as a premium digital commerce and agricultural sourcing experience capable of evolving into a serious production e-commerce platform.

The experience must communicate:

- provenance
- quality
- trust
- sophistication
- agricultural expertise
- Kenyan origin
- global ambition
- modern commerce
- human craftsmanship

The website should feel closer to a premium international food/agricultural brand, specialty exporter, luxury consumer brand, or high-end digital agency project than a typical local business website.

The target reaction is:

> "This feels expensive."

Not:

> "This looks like an AI-generated website."

---

# 02 — BRAND TRUTH

Use real Treadville information whenever available.

Do NOT invent business claims, certifications, partnerships, statistics, awards, customers, export destinations, or product specifications.

Current verified brand information includes:

- Treadville
- Kenyan origin
- Specialty coffee
- Mt. Kenya / Kirinyaga provenance
- 30+ years of combined industry expertise
- Specialty coffees scoring 80+ SCA, with selected lots reaching higher scores
- Traceability
- KEPHIS certification/compliance references
- SGS quality references
- USDA registered warehousing references
- Coffee export capability
- Local Nairobi delivery / pay-on-delivery offering
- Agricultural value creation and market development

The existing brand describes itself as working to transform agricultural resources into real wealth through market development, processing, value addition, and sustainable global networking.

The current site establishes strong provenance around volcanic soils, altitude, glacial water, and Kirinyaga terroir.

Preserve this credibility.

Do not manufacture equivalent claims for Tea, Horticulture, or Grains.

Until the client supplies actual product information, those categories are DEMO CONTENT.

Never present placeholder data as verified Treadville information.

---

# 03 — THE PRODUCT VISION

The current prototype is a vertical slice.

It is NOT the final production system.

The prototype must prove that Treadville can evolve from a coffee-focused website into a multi-category agricultural commerce platform.

Core architecture:

Category
    ↓
Product
    ↓
Product Detail
    ↓
Cart
    ↓
Checkout / Inquiry
    ↓
Admin

The same architecture must support:

- Coffee
- Tea
- Horticulture
- Grains
- future agricultural categories

Do not create separate hard-coded systems for each category.

A new category should be capable of being introduced through data rather than requiring a new page architecture.

---

# 04 — DESIGN NORTH STAR

The visual language is:

PREMIUM
EDITORIAL
ELEGANT
TACTILE
CONFIDENT
MODERN
EARTHED
AFRICAN IN ORIGIN
GLOBAL IN EXECUTION

Avoid anything that looks like:

- generic SaaS
- startup landing page
- AI-generated template
- basic Tailwind demo
- generic Shopify theme
- Canva website
- over-engineered dashboard
- excessive glass cards
- purple/blue AI gradients
- childish animations

The design should feel intentional.

Every major visual decision must answer:

> Why is this here?

---

# 05 — VISUAL DIRECTION

The visual system should draw from:

- volcanic soil
- roasted coffee
- warm earth
- natural stone
- ivory / parchment
- muted metallics
- deep greens
- agricultural textures
- highland landscapes
- premium packaging
- editorial photography

Preferred foundation:

- deep charcoal
- volcanic brown
- espresso
- warm black
- bone / ivory
- muted cream
- restrained bronze / brass
- carefully controlled category accents

Do NOT turn the entire website into brown.

Contrast is essential.

The website should have moments of darkness and moments of light.

---

# 06 — GLASSMORPHISM

Glassmorphism is allowed and encouraged when used with restraint.

Use glass for:

- floating navigation
- cart drawers
- floating controls
- filter panels
- product metadata overlays
- contextual CTAs
- selected admin surfaces
- layered hero interfaces

Glass should feel:

- translucent
- expensive
- subtle
- tactile

Do NOT:

- put glass on every card
- blur every background
- create dozens of floating panels
- use glass simply because it is fashionable

Rule:

> Glass is a material, not a design system.

---

# 07 — TYPOGRAPHY

Typography must feel editorial and premium.

Use a deliberate hierarchy:

- display typography for major statements
- refined serif where appropriate for emotional/editorial moments
- clean sans-serif for UI and commerce
- restrained monospace only for technical/product metadata where useful

Avoid:

- excessive font combinations
- oversized text everywhere
- default browser typography
- inconsistent weights
- random letter spacing

Typography should create rhythm.

Headings should be memorable.

Body copy should be easy to scan.

---

# 08 — LAYOUT PRINCIPLES

Prefer:

- large visual fields
- asymmetry
- strong editorial composition
- generous whitespace
- intentional overlap
- layered imagery
- full-bleed moments
- controlled grids
- visual breathing room

Avoid:

- everything inside cards
- repetitive 3-column layouts
- identical section structures
- excessive rounded rectangles
- narrow content trapped inside generic containers

Not every section needs a card.

Not every element needs a border.

Not every section needs a background color.

---

# 09 — IMAGERY

Photography is a first-class design element.

Images should feel:

- cinematic
- natural
- tactile
- premium
- authentic
- editorial

Prefer:

- farms
- landscapes
- crops
- hands
- harvesting
- processing
- packaging
- product closeups
- atmospheric Kenyan landscapes
- detailed agricultural textures

Avoid:

- obvious corporate stock photography
- fake handshake images
- generic African business imagery
- low-resolution imagery
- repetitive product mockups
- images that have nothing to do with the content

For demo categories, imagery may be sourced externally, but it must be clearly treated as replaceable content.

Never falsely imply a stock image represents a Treadville farm or facility.

---

# 10 — CATEGORY EXPERIENCE

Coffee, Tea, Horticulture and Grains should feel like parts of one ecosystem.

They should NOT look like four unrelated websites.

However, each category may have a distinct visual accent.

Example:

Coffee
    deep espresso / copper

Tea
    deep botanical green

Horticulture
    natural green / fresh earth

Grains
    warm gold / wheat

The accent may influence:

- buttons
- highlights
- metadata
- gradients
- hover states
- imagery treatment
- section details

Do not over-theme the interface.

The Treadville brand remains dominant.

---

# 11 — HERO EXPERIENCE

The homepage hero is one of the most important pieces of the site.

It must communicate the business direction immediately.

The hero should establish:

1. What Treadville is
2. Where it comes from
3. Why it is credible
4. What the user can explore

It should NOT feel like:

"Welcome to our website."

It should feel like the opening frame of a premium brand film.

Potential design techniques:

- cinematic full-screen imagery
- layered typography
- subtle motion
- atmospheric gradients
- foreground/background depth
- floating category navigation
- restrained glass overlays
- animated visual transitions

Do not sacrifice performance for spectacle.

---

# 12 — MOTION SYSTEM

Motion should be sophisticated and purposeful.

Use:

- smooth reveal animations
- staggered entrances
- image scale transitions
- hover transformations
- subtle parallax
- elegant navigation transitions
- product image transitions
- cart micro-interactions
- category transitions
- scroll-linked effects where appropriate

Motion should feel:

- slow enough to feel premium
- fast enough to remain usable
- subtle enough to avoid distraction

Avoid:

- bouncing elements
- excessive spinning
- cartoon animations
- constant movement
- animation on every element
- distracting loaders
- gratuitous particle effects

Rule:

> Motion communicates hierarchy, continuity, or feedback.

If it does none of those, remove it.

---

# 13 — HOVER EFFECTS

Hover states should feel designed.

Examples:

PRODUCT CARD

Default:
- clean image
- product identity
- category
- price/status

Hover:
- image subtly scales
- image crop shifts
- secondary information reveals
- CTA becomes more prominent
- accent appears
- card depth changes subtly

NAVIGATION

Hover:
- underline/reveal indicator
- subtle color transition
- no aggressive movement

BUTTONS

Hover:
- background transition
- slight elevation
- subtle directional motion where appropriate

Do not create exaggerated effects.

---

# 14 — PRODUCT EXPERIENCE

Products are not merely cards.

A product should have a visual story.

Product detail pages should support:

- product identity
- category
- description
- imagery
- price where applicable
- availability
- origin
- quality metadata
- product attributes
- inquiry / purchase CTA
- related products
- category navigation

For coffee, appropriate real data may include:

- grade
- origin
- altitude
- processing method
- tasting notes
- SCA score
- harvest information

Do not fabricate these attributes for placeholder products.

---

# 15 — E-COMMERCE UX

The commerce experience should feel frictionless.

Core flow:

Browse
→ Discover
→ Product
→ Add to cart
→ Cart
→ Checkout / inquiry

Cart interactions should feel immediate.

The cart should communicate:

- product
- quantity
- price
- subtotal
- next action

The prototype does not need live payments.

But the UI must look like a serious commerce system.

Do not create fake payment integrations.

If payment is not implemented, explicitly represent it as a prototype state.

---

# 16 — ADMIN EXPERIENCE

The admin is not an afterthought.

It is one of the strongest demonstrations of the architecture.

The admin should feel like a premium internal product.

It must demonstrate that:

> Treadville can manage its catalogue without calling a developer for every change.

Core prototype areas:

- Dashboard
- Categories
- Products
- Content

The admin must use the same underlying data model as the storefront.

If a category is added in admin:

→ it should become available to the storefront.

If a product is edited:

→ the storefront should reflect the change.

Do not create fake admin screens that merely look functional.

Where functionality is claimed, make it work.

---

Product

---

# 18 — SOURCE OF TRUTH

Use the existing data layer.

Prefer:

components
    ↓
queries/data layer
    ↓
Supabase

Do not scatter direct database queries throughout the UI.

Keep data access predictable.

Keep business logic separate from presentation.

---

# 19 — SUPABASE

The prototype may use Supabase.

Prototype infrastructure may remain intentionally lightweight.

However:

- never expose service-role keys to the client
- use environment variables
- never hard-code credentials
- do not commit `.env.local`
- keep database access centralized
- preserve the ability to introduce proper authentication and RLS later

Prototype public-write policies are temporary.

They MUST NOT be treated as production security.

Production will require:

- authentication
- authorization
- proper RLS
- role management
- audit logging
- secure server-side mutations

---

# 20 — NEXT.JS RULE

This repository may use a newer Next.js version than an agent expects.

Before modifying Next.js-specific functionality:

READ THE LOCAL NEXT.JS DOCUMENTATION.

Relevant documentation exists inside:

node_modules/next/dist/docs/

Do not blindly rely on historical Next.js knowledge.

Respect the repository's AGENTS.md instructions.

Do not downgrade frameworks merely because an older API is more familiar.

- ProductGallery
- ProductMetadata
- CartDrawer

---

# 22 — DESIGN TOKENS

Centralize:

- colors
- spacing
- radii
- shadows
- typography
- transitions
- category accents
- container widths

Do not scatter arbitrary values everywhere.

If the design changes from:

"premium coffee brand"

to:

"premium agricultural marketplace"

we should be able to evolve the visual system without rewriting the application.

---

# 23 — RESPONSIVE DESIGN

Mobile is not a compressed desktop.

Design mobile intentionally.

Test:

- 320px
- 375px
- 390px
- 430px
- tablet
- desktop
- large desktop

Pay particular attention to:

- navigation
- hero typography
- image cropping
- product grids
- sticky elements
- cart drawer
- buttons
- admin tables
- touch targets

No horizontal overflow.

No microscopic text.

No hover-dependent functionality.

---

# 24 — ACCESSIBILITY

Premium does not mean inaccessible.

Maintain:

- semantic HTML
- keyboard navigation
- visible focus states
- sufficient contrast
- alt text
- accessible buttons
- accessible form labels
- reduced-motion support
- logical heading hierarchy

Do not use animation as the only way to communicate state.

---

# 25 — PERFORMANCE

Visual sophistication must not destroy performance.

Prefer:

- Next/Image
- optimized image dimensions
- lazy loading where appropriate
- minimal client components
- server components where appropriate
- limited JavaScript
- efficient animations
- CSS transforms for motion
- avoiding layout thrashing

Do not add a dependency for something that can be done cleanly with CSS or existing utilities.

---

# 26 — ANIMATION PERFORMANCE

Prefer:

transform
opacity

Avoid animating:

- width
- height
- top
- left
- expensive filters
- large layout properties

unless there is a strong reason.

Use `prefers-reduced-motion`.

---

# 27 — CONTENT RULES

Copy must feel:

- confident
- intelligent
- concise
- premium
- human
- commercially useful

Avoid:

- "Welcome to..."

- meaningless corporate filler
- excessive adjectives

- duplicated components

# 35 — FUNCTIONAL QA

Before completing a meaningful feature:

Run appropriate checks.

At minimum where applicable:

npm run lint

npx tsc --noEmit

For production-facing changes:

npm run build

Do not claim a feature works if it has not been tested.

# 36 — GIT DISCIPLINE

Before major changes:

Check:

git status

After meaningful milestones:

Create a commit.

Commit messages should describe intent.

Examples:

feat: redesign premium storefront hero
feat: add category-driven product architecture
feat: implement admin product management
fix: resolve mobile cart overflow
refactor: centralize product queries

Never commit:

- `.env.local`
- secrets
- API keys
- credentials

---

# 37 — AGENT WORKFLOW

When given a task:

STEP 1
Inspect the existing implementation.

STEP 2
Understand the relevant data model.

STEP 3
Identify reusable components.

STEP 4
Determine whether the change is architectural, visual, or both.

STEP 5
Implement the smallest coherent solution.

STEP 6
Run checks.

STEP 7
Inspect for visual regressions.

STEP 8
Report what changed and what remains.

Do not immediately rewrite large sections of the application without understanding them.

---

# 38 — WHEN DESIGNING SOMETHING NEW

Before implementing a new section, ask:

1. What is the user's goal?
2. What is the commercial goal?
3. What information deserves visual priority?
4. What is the emotional impression?
5. What should happen on interaction?
6. Does this feel like Treadville?
7. Does this feel premium?
8. Does this still work on mobile?
9. Is this reusable?
10. Is this necessary?

---

# 39 — PREMIUM QUALITY TEST

Before shipping a visual section, mentally compare it against:

- premium international e-commerce
- luxury food brands
- specialty coffee brands
- premium agricultural exporters
- high-end digital agency work
- modern editorial websites

Ask:

> Would a serious design agency be embarrassed to show this?

If yes:

Improve it.

A premium experience usually has:

- fewer but stronger elements
- better typography
- better photography
- more whitespace
- stronger composition
- subtle motion
- consistent details
- confident copy
- excellent interaction design

It does NOT require:

- more gradients
- more animations
- more shadows
- more cards
- more colors
- more sections

When in doubt:

REMOVE before ADDING.

- retail commerce

- agricultural sourcing
- category-specific catalogues

# 44 — SECURITY BASELINE

Never:

- expose secrets
- commit credentials
- use service-role keys client-side
- trust client-side authorization
- assume RLS is optional in production
- store sensitive information unnecessarily

Prototype shortcuts must remain clearly separated from production requirements.

---

# 45 — DEPENDENCY PRINCIPLE

Before installing a new package ask:

Can this be done with:

- existing project dependencies?
- CSS?
- browser APIs?
- React?
- Next.js?
- Tailwind?

If yes, prefer the existing stack.

A premium website is not made premium by having 73 npm dependencies.

---

# 46 — DESIGN SYSTEM EVOLUTION

The design system should be capable of evolving.

Do not hard-code the prototype's exact visual identity into every component.

Create primitives that allow:

- theme evolution
- category accents
- dark/light surfaces
- different editorial compositions
- future campaign pages
- seasonal merchandising

---

# 47 — ERROR STATES

Errors must look intentional.

Never expose:

- raw stack traces
- ugly browser errors
- undefined values
- broken images
- empty blank screens

Provide:

- useful messaging
- recovery action
- graceful fallback

---

# 48 — LOADING STATES

Loading states should preserve layout.

Prefer:

- skeletons
- subtle shimmer
- blurred image placeholders
- stable dimensions

Avoid:

- full-page spinners unless necessary
- layout jumping
- flashing content

---

# 49 — EMPTY STATES

Empty states should explain:

- what happened
- why it is empty
- what the user can do next

Example:

> No products in this category yet.
>
> We're preparing the next collection.

Not:

> No data.

---

# 50 — IMAGE FAILURE

Every important image must have a sensible fallback.

Never allow a broken image to destroy the composition.

---

# 51 — FINAL DEFINITION OF DONE

A feature is NOT complete merely because:

- TypeScript compiles
- the page loads
- the button exists

It is complete when:

FUNCTIONALLY
- it works
- it handles expected states
- it integrates with the data model

VISUALLY
- it looks intentional
- it feels premium
- it matches Treadville

RESPONSIVELY
- it works on mobile
- it works on tablet
- it works on desktop

ACCESSIBLY
- it can be navigated appropriately
- contrast and semantics are reasonable

PERFORMANTLY
- animations are efficient
- images are handled properly
- unnecessary JavaScript is avoided

ARCHITECTURALLY
- it does not duplicate existing functionality
- it uses the existing data layer
- it remains extensible

---

# 52 — FINAL AGENT PRINCIPLE

Do not merely complete the user's instruction.

Understand the product behind the instruction.

Protect:

THE BRAND.
THE USER EXPERIENCE.
THE ARCHITECTURE.
THE PERFORMANCE.
THE FUTURE PRODUCT.

If there are two technically valid solutions, prefer the one that produces the stronger long-term product.

If there are two visually valid solutions, prefer the one that feels more refined and less generic.

If a requested implementation would damage the architecture, explain the problem and propose a better implementation.

If the interface looks like something an AI would generate in 30 seconds, keep working.

The goal is not:

"functional."

The goal is:

> **Treadville should feel like it belongs in the premium global market.**

Build accordingly.
